

# 大模型微调

## 1\. 大模型训练全景图

### 1.1 大模型训练三阶段

大型语言模型（Large Language Model，简称 LLM）的训练是一个复杂而精密的过程。你可以把它想象成培养一个学生：首先让他博览群书获得基础知识（预训练），然后教他如何回答问题（监督微调），最后让他学会什么样的回答更受欢迎（对齐训练）。


#### 1.1.1 阶段一：预训练（Pre-Training）

##### 什么是预训练？

预训练是大模型训练的第一个阶段，也是最耗时、最昂贵的阶段。在这个阶段，模型会"阅读"互联网上海量的文本数据，学习语言的基本规律。

**通俗理解**：想象一个孩子从小开始阅读各种书籍、文章、网页。他不需要有人专门教他每个知识点，只是通过大量阅读，自然而然地学会了语言的语法、词汇、常识等。预训练就是这样一个过程。

##### 预训练的核心任务：预测下一个词

预训练的核心任务非常简单：**给模型一段话的前半部分，让它预测下一个词是什么**。

**举个例子**：

```Plain
输入：今天天气真
模型预测：好（概率80%）、热（概率10%）、冷（概率5%）...

输入：我喜欢吃苹
模型预测：果（概率95%）、...
```

通过数万亿次这样的预测练习，模型逐渐学会了：

-   **语法规则**：主语后面通常跟谓语

-   **常识知识**：苹果是一种水果，可以吃

-   **世界知识**：北京是中国的首都

-   **推理能力**：如果 A 大于 B，B 大于 C，那么 A 大于 C

##### 什么是 Token？

Token 是模型处理文本的基本单位，这是理解大模型的重要概念。

**Token 不等于字或词**：

-   英文中，一个常见单词通常是 1 个 Token，复杂词可能被拆成多个

-   中文中，一个汉字通常是 1-2 个 Token

-   标点符号、空格等也会占用 Token

**举例说明**：

|     |     |     |
| --- | --- | --- |
| **文本** | **Token 数（约）** | **说明** |
| Hello | 1   | 常见英文词 |
| extraordinary | 3   | 会被拆分 |
| 你好  | 2   | 两个汉字 |
| 人工智能 | 2月3日 | 常见词可能被整体编码 |

**为什么 Token 很重要？**

-   模型的**上下文长度**以 Token 计算（如 Qwen3 支持 128K Token）

-   **训练成本**按 Token 数量计算

-   **API 定价**按输入输出 Token 数计费

##### 预训练需要什么样的数据？

|     |     |     |
| --- | --- | --- |
| **数据类型** | **来源举例** | **作用** |
| 网页文本 | 维基百科、新闻网站、博客 | 学习通用知识和语言表达 |
| 书籍  | 小说、教材、专业书籍 | 学习深度知识和长文本理解 |
| 论文  | arXiv、学术期刊 | 学习专业术语和科学知识 |
| 代码  | GitHub 开源项目 | 学习编程语言和逻辑思维 |
| 对话  | 社交媒体、论坛 | 学习日常对话和口语表达 |

**数据规模有多大？**

|     |     |     |
| --- | --- | --- |
| **模型** | **训练数据量** | **说明** |
| GPT-3 | 约 3000 亿 Token | 2020 年 |
| LLaMA-2 | 约 2 万亿 Token | 2023 年 |
| Qwen3 | 约 36 万亿 Token | 2025 年 |
| GPT-4 | 估计 13 万亿+ Token | 未公开 |

可以看到，训练数据量在快速增长，这是模型能力提升的重要原因之一。

##### 预训练后的模型能做什么？

预训练完成后，我们得到的是一个 **Base Model（基座模型）**。这个模型已经具备了丰富的知识，但它有一个重要的问题：**它不会对话**。

**Base Model 的行为特点**：

```Plain
用户输入：请介绍一下北京
Base Model 输出：的历史。北京是中国的首都，有着悠久的历史...
（它会继续写下去，而不是回答问题）

用户输入：1+1等于几？
Base Model 输出：2+2等于4，3+3等于6...
（它会继续写下去，像在续写数学练习题）
```

这是因为 Base Model 学到的是"续写"文本，而不是"回答问题"。要让模型学会对话，我们需要进行下一个阶段的训练。

#### 1.1.2 阶段二：监督微调（Supervised Fine-Tuning，SFT）

##### 什么是监督微调？

监督微调（SFT）是让模型学会"听话"的关键阶段。在这个阶段，我们用大量的"问题-答案"对来训练模型，教它：当用户问问题时，应该给出答案，而不是继续往下写。

**通俗理解**：如果说预训练是让学生读了很多书，那么 SFT 就是教学生如何回答老师的问题。老师问"北京是哪个国家的首都？"，学生应该回答"中国"，而不是继续念课文。

##### SFT 数据长什么样？

SFT 使用的是**指令数据**，每条数据包含输入和期望的输出：

```JSON
{
  "instruction": "请将以下英文句子翻译成中文",
  "input": "The weather is nice today.",
  "output": "今天天气很好。"
}
```

或者更简单的问答格式：

```JSON
{
  "instruction": "中国的首都是哪里？",
  "input": "",
  "output": "中国的首都是北京。北京位于中国北部，是中国的政治、文化中心。"
}
```

##### SFT 数据的类型

|     |     |     |
| --- | --- | --- |
| **任务类型** | **指令示例** | **输出示例** |
| 问答  | 什么是光合作用？ | 光合作用是植物利用阳光将二氧化碳和水转化为葡萄糖和氧气的过程... |
| 翻译  | 将"Hello"翻译成中文 | 你好  |
| 摘要  | 请总结以下文章的主要内容 | 这篇文章主要讲述了... |
| 写作  | 写一首关于春天的诗 | 春风拂面百花开，万紫千红总是春... |
| 代码  | 写一个 Python 函数计算斐波那契数列 | def fibonacci(n): ... |
| 推理  | 小明比小红高，小红比小刚高，谁最高？ | 根据题目条件，小明最高... |

##### SFT 需要多少数据？

与预训练相比，SFT 需要的数据量小得多，但**质量要求更高**。

|     |     |     |
| --- | --- | --- |
| **任务复杂度** | **建议数据量** | **说明** |
| 简单任务（如分类） | 500-2000 条 | 任务单一，规则明确 |
| 中等任务（如客服问答） | 2000-10000 条 | 需要覆盖多种场景 |
| 复杂任务（如通用对话） | 10000-100000 条 | 需要极高的多样性 |

**重要原则：质量 > 数量**

10000 条高质量数据的效果，往往比 100000 条低质量数据更好。高质量数据的特点：

-   答案准确、专业

-   表达流畅、自然

-   格式统一、规范

-   覆盖场景多样

##### SFT 后的模型有什么变化？

|     |     |     |
| --- | --- | --- |
| **对比项** | **Base Model** | **SFT 后的 Model** |
| 输入理解 | 当作续写任务 | 理解为指令/问题 |
| 输出方式 | 无限续写 | 给出完整答案后停止 |
| 对话能力 | 几乎没有 | 可以进行基本对话 |
| 指令遵循 | 无法遵循 | 能按指令执行任务 |

**实际效果对比**：

```Python
【Base Model】
用户：请用三句话介绍自己
模型：。我是一个人工智能助手。我可以帮助你回答问题。
      我喜欢学习新知识。今天的天气很好，我们可以...（停不下来）

【SFT 后的 Model】
用户：请用三句话介绍自己
模型：我是一个人工智能助手。我可以帮助你回答各种问题、完成各类任务。
      我的目标是为你提供准确、有用的信息。（完整回答后停止）
```

#### 1.1.3 阶段三：对齐训练（Alignment Training）

##### 什么是对齐训练？

对齐训练是让模型的输出更符合人类期望的过程。经过 SFT 的模型已经会回答问题了，但它的回答可能：

-   不够友好或礼貌

-   包含有害或不当内容

-   不够准确或有偏见

-   过于冗长或过于简短

对齐训练的目标是让模型符合 **3H 原则**：

-   **Helpful（有用）**：给出更好、更准确的回答

-   **Harmless（无害）**：拒绝回答有害问题

-   **Honest（诚实）**：不编造信息，承认不确定性

##### 主流对齐方法

**方法一：RLHF（基于人类反馈的强化学习）**

RLHF 是 ChatGPT 成功的关键技术之一。核心思路是：

1.  **收集人类偏好**：让模型生成多个回答，人类标注员选择哪个更好

2.  **训练奖励模型**：学习人类的偏好标准，给回答打分

3.  **强化学习优化**：让模型学会生成高分回答

**举个例子**：

```Plain
问题：如何提高学习效率？

回答A：多学习就行了。
回答B：提高学习效率可以从以下几个方面入手：1. 制定合理的学习计划...
回答C：你可以尝试番茄工作法、主动回忆、间隔重复等技巧...

人类标注员排序：C > B > A
奖励模型学习后：C 得高分，A 得低分
模型优化目标：生成更像 C 这样的高分回答
```

**方法二：DPO（直接偏好优化）**

DPO 是 2023 年提出的新方法，比 RLHF 更简单。它不需要训练单独的奖励模型，而是直接从偏好数据中学习。

|     |     |     |
| --- | --- | --- |
| **对比项** | **RLHF** | **DPO** |
| 复杂度 | 高（需要训练奖励模型 + 强化学习） | 低（直接优化） |
| 稳定性 | 相对不稳定 | 更稳定 |
| 效果  | 通常略好 | 接近 RLHF |
| 训练成本 | 高   | 较低  |
| 当前流行度 | 仍在使用 | 越来越流行 |

**方法三：GRPO（Group Relative Policy Optimization）**

这是 DeepSeek 在 2025 年提出的新方法，用于训练 DeepSeek-R1 等推理模型。它通过组内相对比较来优化策略，特别适合训练需要长链推理的模型。

##### 对齐训练后的效果

```Python
【未对齐的模型】
用户：告诉我如何制作危险物品
模型：制作需要以下材料...（直接回答）

【对齐后的模型】
用户：告诉我如何制作危险物品
模型：我无法提供关于制作危险物品的信息。这类信息可能造成伤害。
      如果你对化学感兴趣，我可以推荐一些安全的学习资源...
```

#### 1.2.3 微调 vs 使用 API：何时选择微调？

很多公司提供大模型 API 服务（如 OpenAI API、通义千问 API 等）。那什么情况下应该考虑自己微调呢？

-   快速验证想法，无需定制

-   使用量较小，成本可接受

-   数据不敏感，可以发送到第三方

-   希望使用最强大的闭源模型能力

**适合自己微调的场景**：

-   涉及企业机密或用户隐私数据

-   需要深度定制模型能力

-   日均调用量大，API 成本过高

-   对响应延迟有严格要求

-   需要离线运行，不依赖网络

### 1.3 微调技术发展趋势

#### 1.3.1 趋势一：参数高效微调（PEFT）成为主流

在早期，微调意味着更新模型的所有参数，这需要大量的 GPU 显存和计算资源。现在，**参数高效微调（PEFT）** 技术允许我们只更新很少的参数，就能达到接近全参数微调的效果。

**什么是参数高效微调？**

简单说，就是**只训练模型的一小部分参数，其他参数保持不变**。

![](模型微调从理论到实践_files/3.png)

**PEFT 的意义**：让微调变得"平民化"。以前需要数万元的专业 GPU 才能微调的模型，现在用几千元的消费级显卡就能完成。

其中 Dense（稠密）模型是一类**全参数激活**的神经网络架构，在每次前向传播中，所有参数都会参与计算，形成**全连接**的特性。

#### 1.3.2 趋势二：MoE（混合专家）模型兴起

2024-2025 年，MoE（Mixture of Experts，混合专家）架构成为大模型的热门选择。

**什么是 MoE？**

传统的模型在处理每个问题时，所有参数都会参与计算。而 MoE 模型包含多个"专家"网络，处理问题时只激活其中几个相关的专家。

**通俗理解**：

-   传统模型 = 一个全科医生处理所有病人

-   MoE 模型 = 有内科、外科、儿科等多个专家，根据病人情况分配给合适的专家

![](模型微调从理论到实践_files/4.png)

**MoE 模型的优势**：

|     |     |
| --- | --- |
| **优势** | **说明** |
| 参数量大但计算快 | 总参数很多，但每次只用一部分 |
| 能力更强 | 专家分工，各司其职 |
| 推理效率高 | 激活参数少，推理速度快 |

**代表性 MoE 模型（2025 年）**：

|     |     |     |     |
| --- | --- | --- | --- |
| **模型** | **总参数量** | **每次激活参数** | **说明** |
| DeepSeek-V3.1 | 6710 亿 | 约 370 亿 | 目前最强开源模型之一 |
| Qwen3-235B-A22B | 2350 亿 | 约 220 亿 | 阿里最新 MoE 模型 |
| Qwen3-30B-A3B | 300 亿 | 约 30 亿 | 轻量级 MoE，效率高 |
| LLaMA 4 Maverick | 4000 亿 | 约 170 亿 | Meta 最新多模态模型 |

#### 1.3.3 趋势三：推理模型（Reasoning Model）的崛起

2024 年底，OpenAI 发布了 o1 模型，开创了"推理模型"这一新品类。随后，DeepSeek 发布了开源的 DeepSeek-R1，引发了广泛关注。

**什么是推理模型？**

推理模型的特点是：**在回答问题前，会先进行长链条的思考**。

**普通模型 vs 推理模型**：

```Python
问题：一个水池有两个水管，单开 A 管 3 小时注满，单开 B 管 5 小时注满，
      同时开两管几小时注满？

【普通模型】
答案：同时开两管 1.875 小时注满。
（直接给出答案，但可能出错）

【推理模型】
让我思考一下这个问题...

首先，这是一个工程问题，涉及到两个水管的工作效率。

A 管的效率：1 小时可以注满 1/3 的水池
B 管的效率：1 小时可以注满 1/5 的水池

同时开两管的效率：1/3 + 1/5 = 5/15 + 3/15 = 8/15

设需要 y 小时注满，则：
8/15 × y = 1
y = 15/8 = 1.875 小时

让我验证一下：
A 管在 1.875 小时注入：1.875 × (1/3) = 0.625
B 管在 1.875 小时注入：1.875 × (1/5) = 0.375
总计：0.625 + 0.375 = 1（正好注满）✓

答案：同时开两管 1.875 小时（即 1 小时 52.5 分钟）可以注满水池。
```

**推理模型的特点**：

|     |     |
| --- | --- |
| **特点** | **说明** |
| 思维链（Chain of Thought） | 展示详细的思考过程 |
| 自我验证 | 检查答案是否正确 |
| 反思纠错 | 发现错误会自我纠正 |
| 复杂推理能力强 | 在数学、编程、逻辑题上表现出色 |

**代表性推理模型**：

|     |     |     |     |
| --- | --- | --- | --- |
| **模型** | **开发者** | **是否开源** | **特点** |
| o1 / o3 | OpenAI | 否   | 推理能力最强，但闭源 |
| DeepSeek-R1-0528 | DeepSeek | 是   | 最强开源推理模型 |
| DeepSeek-V3.1 | DeepSeek | 是   | 混合思维模式 |
| Qwen3 系列 | 阿里巴巴 | 是   | 支持 Thinking/Non-Thinking 模式 |

**混合思维模式**

**同一个模型支持两种模式**：

-   **Thinking Mode（思维模式）**：深度推理，适合复杂问题

-   **Non-Thinking Mode（快速模式）**：直接回答，适合简单问题

用户可以根据需要切换模式，这在 Qwen3 和 DeepSeek-V3.1 中已经实现。

## 2\. 主流微调方法详解

### 2.1 计算机中的数字表示基础

在深入讲解微调方法之前，我们需要先理解一些基础概念。

#### 2.1.1 什么是浮点数（FP）？

计算机中的数字有不同的表示方式。在大模型训练中，最常见的是**浮点数（Floating Point，简称 FP）**。

**为什么叫"浮点"？**

因为小数点的位置可以"浮动"。比如 123.456 和 0.00123456 都可以用科学计数法表示，小数点根据指数"浮动"。

#### 2.2.2 常见的数字精度类型

计算机用不同的位数来存储数字，位数越多，精度越高，但占用空间也越大。

|     |     |     |     |     |
| --- | --- | --- | --- | --- |
| **类型** | **全称** | **占用空间** | **精度** | **用途** |
| FP32 | 32位浮点数 | 4 字节 | 约 7 位有效数字 | 传统训练的标准精度 |
| FP16 | 16位浮点数 | 2 字节 | 约 3 位有效数字 | 混合精度训练 |
| BF16 | Brain Float 16 | 2 字节 | 约 2-3 位有效数字 | 大模型训练常用 |
| INT8 | 8位整数 | 1 字节 | 整数  | 模型量化推理 |
| INT4 | 4位整数 | 0.5 字节 | 整数（仅16个值） | 极致压缩 |

**通俗理解精度与空间的关系**：

想象你在描述一个人的身高：

-   **FP32**：精确到 0.0001 毫米（1.750123 米），非常精确，但需要更多存储

-   **FP16**：精确到 0.1 毫米（1.750 米），精度降低，但存储减半

-   **INT8**：只记录整数厘米（175 厘米），精度更低，但存储更少

-   **INT4**：只记录大概范围（如 170-180 厘米区间），极致压缩

#### 2.2.3 为什么精度很重要？

|     |     |     |
| --- | --- | --- |
| **场景** | **精度要求** | **说明** |
| 训练时 | 较高（FP32/BF16） | 梯度计算需要精确 |
| 推理时 | 可以较低（INT8/INT4） | 速度更快，精度损失小 |
| 微调时 | 混合使用 | 原始参数低精度，新参数高精度 |

### 2.2 全参数微调（Full Fine-tuning）

#### 2.2.1 什么是全参数微调？

全参数微调是最直接的微调方式：**更新模型的所有参数**。

**通俗理解**：如果把模型比作一本教科书，全参数微调就是把书中的每一页都可能修改。

![](模型微调从理论到实践_files/5.png)

#### 2.2.2 全参数微调的优缺点

**优点**：

|     |     |
| --- | --- |
| **优点** | **详细说明** |
| 效果最佳 | 可以充分调整模型，适应新任务 |
| 无额外结构 | 微调后模型结构不变，部署简单 |
| 适应性强 | 适合需要大幅改变模型能力的场景 |

**缺点**：

|     |     |
| --- | --- |
| **缺点** | **详细说明** |
| 显存需求巨大 | 需要存储模型、梯度、优化器状态 |
| 训练成本高 | 需要昂贵的 GPU，训练时间长 |
| 灾难性遗忘 | 可能丢失预训练学到的通用能力 |
| 过拟合风险 | 数据量小时容易过拟合 |
| 存储成本高 | 每个任务保存一份完整模型 |

#### 2.2.3 什么是灾难性遗忘？

**灾难性遗忘（Catastrophic Forgetting）** 是深度学习中的一个经典问题：当模型学习新任务时，可能会忘记之前学过的知识。

**举例说明**：

```Python
【微调前】
问：中国的首都是哪里？
答：北京

问：1+1等于几？
答：2

【用客服数据微调后，发生灾难性遗忘】
问：中国的首都是哪里？
答：很抱歉，这个问题不在我们的服务范围内...（忘记了常识）

问：1+1等于几？
答：请问您咨询的是什么产品？（完全跑偏）
```

**如何缓解灾难性遗忘？**

|     |     |
| --- | --- |
| **方法** | **说明** |
| 降低学习率 | 用更小的学习率，让参数变化更温和 |
| 混合训练数据 | 在微调数据中混入通用数据 |
| 正则化 | 限制参数变化的幅度 |
| 使用 PEFT 方法 | 只改变少量参数，原始能力保留更多 |

### 2.3 参数高效微调（PEFT）概述

#### 2.3.1 PEFT 的核心思想

PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）的核心思想是：**只训练模型的一小部分参数，冻结大部分原始参数**。

**形象比喻**：

-   **全参数微调** = 把整本教科书重写

-   **PEFT** = 在教科书上贴便利贴做补充

### 2.4 LoRA：最流行的微调方法

LoRA（Low-Rank Adaptation，低秩适应）是目前最流行的 PEFT 方法，由微软在 2021 年提出。

#### 2.4.1 LoRA 的核心思想

**问题**：模型参数矩阵动辄上亿个参数，直接训练太大了。

**LoRA 的解决方案**：用两个小矩阵的乘积，来**近似**原本需要学习的大矩阵更新。

**通俗理解**：

假设你要调整一个 1000×1000 的参数矩阵（100 万个参数）：

-   **全参数微调**：直接学习 100 万个参数的变化

-   **LoRA**：学习两个小矩阵 1000×8 和 8×1000（共 1.6 万个参数），用它们的乘积来近似那 100 万个参数的变化

参数量减少了 **60 倍以上**！

#### 2.4.2 LoRA 的数学原理

原始的权重更新可以表示为：

$$W' = W + \Delta W $$

其中 $ W $ 是原始权重， $ \Delta W $是需要学习的更新。

LoRA 的关键假设是： $$\Delta W $$**可以分解为两个低秩矩阵的乘积**：

$$\Delta W = B \times A $$

其中：

-   $ W $的维度是 $d \times k $（比如 4096 × 4096）

-   $ B $ 的维度是 $ d \times r $（比如 4096 × 16）

-   $ A $ 的维度是 $ r \times k $（比如 16 × 4096）

-   $ r $是秩（rank），通常取 8-64，远小于 d 和 k

**为什么这样可行？**

研究发现，微调时权重的变化往往是"低秩"的——变化集中在少数几个方向上。这意味着我们不需要学习全部参数，只需要学习关键的几个"方向"。

#### 2.4.3 LoRA 的工作流程

![](模型微调从理论到实践_files/8.png)

**工作流程解释**：

1.  **原始路径**：输入通过冻结的权重 W，产生原始输出

2.  **LoRA 路径**：输入同时通过 A 矩阵（降维），再通过 B 矩阵（升维），产生增量输出

3.  **缩放**：LoRA 输出乘以 α/r 进行缩放

4.  **最终输出**：原始输出 + 缩放后的 LoRA 输出

#### 2.4.4 LoRA 的关键参数

使用 LoRA 时，需要配置几个重要参数：

**1\. r（秩，Rank）**

这是最重要的参数，决定了 LoRA 的"容量"。

|     |     |     |     |
| --- | --- | --- | --- |
| **r 值** | **可训练参数量** | **效果** | **适用场景** |
| 4-8 | 极少  | 可能不足 | 非常简单的任务、快速实验 |
| 16  | 少   | 较好  | **大多数任务的推荐值** |
| 32  | 适中  | 好   | 复杂任务 |
| 64  | 较多  | 很好  | 需要高质量的复杂任务 |
| 128 | 很多  | 接近全参数 | 特殊需求 |

| **常见设置** | **含义** |

**推荐**：通常设置 `alpha = 2 × r`，即 r=16 时 alpha=32。

|     |     |
| --- | --- |
| **优势** | **详细说明** |
| **显存大幅降低** | 只需存储少量可训练参数的梯度和优化器状态 |
| **训练速度快** | 计算量大幅减少 |
| **可以合并** | 训练完成后，LoRA 可以合并到原模型，推理无额外开销 |
| **可以叠加** | 一个模型可以有多个 LoRA，切换任务时只需切换 LoRA |
| **减少过拟合** | 参数少，不容易过拟合 |
| **保留原始能力** | 原始参数不变，灾难性遗忘减少 |

### 2.5 QLoRA：让消费级显卡也能微调大模型

QLoRA（Quantized LoRA）是 2023 年提出的技术，它让**普通消费级显卡也能微调大模型**。

#### 2.5.1 QLoRA 的核心思想

QLoRA = **模型量化** + **LoRA**

-   **量化（Quantization）**：把模型参数从 FP16 压缩到 4-bit，大幅减少存储

-   **LoRA**：只训练少量参数

![](模型微调从理论到实践_files/11.png)

#### 2.5.2 QLoRA 的三大核心技术

**技术一：4-bit NormalFloat（NF4）量化**

普通的 4-bit 量化假设数值均匀分布，但神经网络权重通常呈正态分布。

NF4 是专门为正态分布设计的 4-bit 数据类型，量化误差更小。

**技术二：双重量化（Double Quantization）**

量化需要存储缩放因子，双重量化对缩放因子再进行一次量化，进一步节省空间。

**技术三：分页优化器（Paged Optimizer）**

当 GPU 显存不够时，自动把优化器状态转移到 CPU 内存，避免溢出。

#### 2.5.3 QLoRA 的效果

很多人担心：压缩这么多，效果会不会差很多？

研究表明：**QLoRA 的效果与 FP16 LoRA 非常接近**，在大多数任务上差距小于 1%。

|     |     |     |
| --- | --- | --- |
| **方法** | **相对效果** | **说明** |
| 全参数微调（FP16） | 100% | 基准  |
| LoRA（FP16） | 约 98% | 接近全参数 |
| QLoRA（4-bit） | 约 97% | 接近 LoRA |

### 2.6 LoRA 的进阶变体

#### 2.6.1 DoRA（Weight-Decomposed LoRA）

**核心思想**：把权重分解为"方向"和"幅度"两个部分，分别学习。

**通俗理解**：

想象调整一个向量：

-   **LoRA**：直接调整向量的整体

-   **DoRA**：分开调整向量的方向（指向哪里）和长度（有多长）

**DoRA 的优势**：

|     |     |
| --- | --- |
| **优势** | **说明** |
| 效果更好 | 在多个基准测试上超过 LoRA |
| 更接近全参数微调 | 分解更灵活 |
| 参数量相近 | 只增加了一个幅度向量 |

#### 2.6.2 LoRA+

**核心思想**：对 A 和 B 矩阵使用不同的学习率。

研究发现，B 矩阵需要比 A 矩阵更大的学习率才能获得最佳效果。

#### 2.6.3 rsLoRA（Rank-Stabilized LoRA）

**核心思想**：修改缩放系数，使不同秩的 LoRA 有更一致的训练动态。

当改变秩 r 时，普通 LoRA 的效果会不稳定，rsLoRA 解决了这个问题。

# 模块二：硬件配置与环境搭建

## 1\. 模型规模与算力需求

**核心问题：我的显卡能不能微调大模型？**

### 1\. 基础概念

#### 1.1 推理 vs 微调

这两个概念是理解显存需求的基础：

|     |     |     |
| --- | --- | --- |
| **对比项** | **推理 (Inference)** | **微调 (Fine-tuning)** |
| 目的  | 使用模型生成结果 | 训练模型学习新知识 |
| 参数变化 | 不变  | 更新  |
| 显存占用 | 低 (约 1x) | 高 (约 4-6x) |
| 计算复杂度 | 低   | 高   |
| 典型场景 | 聊天、问答 | 定制化训练 |

**形象比喻：**

-   推理 = 开卷考试：你只需要「看」书本（模型参数），然后写出答案

-   微调 = 学习过程：你需要「看」书本、「做」练习题、「记」错题本、「改」学习方法

**核心差异：** 推理只需要「使用」模型，而微调需要「训练」模型——这意味着微调需要存储更多的中间数据。

#### 1.2 什么是显存（VRAM）？

显存（Video Random Access Memory）是显卡专用的内存，用于存储 GPU 计算所需的数据。

|     |     |     |
| --- | --- | --- |
| **类型** | **说明** | **比喻** |
| 内存 (RAM) | CPU 使用的通用内存 | 厨房的储物柜 |
| 显存 (VRAM) | GPU 专用的高速内存 | 灶台的操作空间 |

**生活化比喻：**

```Plain
┌─────────────────────────────────────────────────────────┐
│                      厨房比喻                            │
├─────────────────────────────────────────────────────────┤
│  储物柜 (内存)          灶台 (显存)                       │
│  ┌─────────┐          ┌─────────────────┐               │
│  │ 食材储存 │    →     │  实际烹饪空间    │               │
│  │ 容量大   │          │  决定同时处理量  │               │
│  │ 存取慢   │          │  高速访问       │               │
│  └─────────┘          └─────────────────┘               │
└─────────────────────────────────────────────────────────┘
```

灶台空间（显存）决定了你能同时处理多少食材（数据），如果灶台太小，就只能分批处理。

### 2\. 微调为什么需要更多显存？

#### 2.1 推理 vs 微调的显存占用对比

**显存占用对比表：**

|     |     |     |     |
| --- | --- | --- | --- |
| **组件** | **推理时** | **微调时** | **说明** |
| 模型参数 | ✅ 需要 | ✅ 需要 | 基础占用 |
| 梯度  | ❌ 不需要 | ✅ 需要 | 每个参数对应一个梯度 |
| 优化器状态 | ❌ 不需要 | ✅ 需要 | Adam 需要 2 倍参数量 |
| 激活值 | 少量  | 大量  | 反向传播需要保存 |
| **总计倍数** | **~1x** | **~4-6x** | 微调显存是推理的 4-6 倍 |

下面我们逐一详解每个组件。

#### 2.2 梯度（Gradients）详解

**什么是梯度？**

梯度是一个数学概念，它告诉模型每个参数应该往哪个方向调整、调整多少。

**数学直觉（理解概念即可）：**

```Bash
想象你站在一座山上，想要走到山谷最低点（这个最低点代表模型的最优状态）：

        你在这里 →  ⛷️
                    ╱╲
                   ╱  ╲
                  ╱    ╲
                 ╱      ╲
             ───╱────────╲───  ← 山谷（最优解）

- 梯度 = 你脚下地面的「坡度」和「方向」
- 正梯度 = 地面往上倾斜 → 你应该往反方向走（往下）
- 负梯度 = 地面往下倾斜 → 你应该顺着这个方向走
- 梯度为零 = 你已经到达山谷底部（或山顶）
```

**梯度的计算过程**

![](模型微调从理论到实践_files/14.png)

反向传播使用链式法则，从输出层向输入层逐层计算梯度。就像多米诺骨牌，从最后一张牌（损失）开始，依次影响前面的每一张牌（每一层）。

**显存占用**

每个参数需要一个对应的梯度值。

|     |     |     |     |
| --- | --- | --- | --- |
| **模型** | **参数数量** | **FP32 梯度显存** | **BF16 梯度显存** |
| 8B 模型 | 80 亿 | 80亿 × 4字节 = 32 GB | 80亿 × 2字节 = 16 GB |
| 14B 模型 | 140 亿 | 140亿 × 4字节 = 56 GB | 140亿 × 2字节 = 28 GB |

#### 2.3 优化器（Optimizer）详解

**什么是优化器？**

优化器决定「如何根据梯度来调整参数」。

如果说梯度告诉你「往哪走」，那么优化器决定「怎么走」——是大步快走，还是小步慢走？遇到坑洼地怎么办？

**最简单的优化器：SGD（随机梯度下降）**

```Python
# SGD 的核心思想（伪代码）
新参数 = 旧参数 - 学习率 × 梯度
```

**比喻：盲人下山**

-   你蒙着眼睛站在山上

-   每次用脚试探周围地面的坡度（计算梯度）

-   然后往下坡方向走一小步（更新参数）

-   重复这个过程直到到达山谷

**SGD 的问题：**

-   容易在山谷附近来回震荡

-   遇到平坦区域会走得很慢

-   不同参数可能需要不同的步长

**现代优化器：Adam / AdamW**

Adam（Adaptive Moment Estimation）是当前最常用的优化器，它解决了 SGD 的问题。

**Adam 两个关键组件：**

-   **一阶动量 (m)**：梯度的移动平均，作用是平滑梯度减少震荡，比喻为「惯性」

-   **二阶动量 (v)**：梯度平方的移动平均，作用是自适应学习率，比喻为「变速器」

**存储需求：**

|     |     |     |
| --- | --- | --- |
| **存储项** | **数量** | **说明** |
| 一阶动量 (m) | 与参数量相同 | 每个参数 1 个数值 |
| 二阶动量 (v) | 与参数量相同 | 每个参数 1 个数值 |
| **总计** | **参数量 × 2** | 80 亿参数需存储 160 亿数值 |

**实际计算（以 8B 模型为例）：**

```Plain
模型参数：80 亿个
一阶动量：80 亿个 × 4 字节 = 32 GB（使用 FP32）
二阶动量：80 亿个 × 4 字节 = 32 GB（使用 FP32）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
优化器状态总计：64 GB

注：优化器状态通常使用 FP32 以保证数值稳定性，即使模型本身用 BF16
```

**优化器对比：**

|     |     |     |     |
| --- | --- | --- | --- |
| **优化器** | **额外存储** | **优点** | **缺点** |
| SGD | 0   | 显存占用最小 | 收敛慢，不稳定 |
| SGD + Momentum | 1x 参数量 | 比 SGD 稳定 | 仍需调参 |
| Adam/AdamW | 2x 参数量 | 收敛快，稳定 | 显存占用大 |
| AdaFactor | ~0.5x 参数量 | 折中方案 | 效果略差 |

> **为什么还用 Adam？** 因为它「又快又稳」，虽然显存占用大，但训练效率高，综合下来往往更划算。

#### 2.4 激活值（Activations）详解

**什么是激活值？**

激活值是神经网络在前向计算过程中，每一层产生的中间结果。

**为什么需要保存激活值？**

答案：反向传播的链式法则需要用到这些中间结果。

**类比：查账**

```Plain
想象你在审计一家公司的账目：

原始资金 → [采购部] → 库存 → [生产部] → 产品 → [销售部] → 收入
             ↓                ↓                ↓
           采购记录         生产记录          销售记录

如果你发现最终收入有问题，需要追溯是哪个环节出错：
1. 首先查销售记录（销售部的「激活值」）
2. 然后查生产记录（生产部的「激活值」）
3. 最后查采购记录（采购部的「激活值」）

如果没有保存这些中间记录，你就无法追溯问题！
```

**激活值的显存占用因素：**

|     |     |     |     |
| --- | --- | --- | --- |
| **因素** | 含义  | **影响** | **说明** |
| Batch Size | 一次训练处理多少条数据 | 线性增长 | batch\_size=4 表示同时处理 4 条训练样本 |
| 序列长度 | 每条数据的 token 数量 | 线性增长 | 一段 2048 个字的文本，序列长度就是 2048 |
| 隐藏维度 | 模型内部表示的向量大小 | 线性增长 | Qwen3-8B 的隐藏维度是 4096 |
| 层数  | Transformer 堆叠的层数 | 线性增长 | Qwen3-8B 有 32 层 |

**估算公式（简化版）：**

```Plain
激活值显存 ≈ batch_size × 序列长度 × 隐藏维度 × 层数 × 2字节
```

**实际案例（Qwen3-8B，序列长度 2048，batch\_size=1）：**

```Plain
隐藏维度：4096
层数：32
激活值 ≈ 1 × 2048 × 4096 × 32 × 2 ≈ 0.5 GB

如果 batch_size = 4：
激活值 ≈ 4 × 2048 × 4096 × 32 × 2 ≈ 2 GB
```

**激活值重计算（Gradient Checkpointing）**

```Plain
原始方案（保存所有激活值）：
┌─────────────────────────────────────────────────────────────┐
│  [层1] → 激活1(✅保存) → [层2] → 激活2(✅保存) → [层3] → 激活3(✅保存) → [层4]  │
└─────────────────────────────────────────────────────────────┘

检查点方案（只保存部分）：
┌─────────────────────────────────────────────────────────────┐
│  [层1] → 激活1(✅保存) → [层2] → 激活2(❌丢弃) → [层3] → 激活3(✅保存) → [层4]  │
│                                   ↑                                     │
│                        反向传播时：从激活1重新计算激活2                    │
└─────────────────────────────────────────────────────────────┘
```

**权衡：**

-   ✅ 优点：节省显存（可以减少 50-70%）

-   ❌ 缺点：增加计算时间（约 20-30%）

### 3\. 显存计算方法

#### 3.1 数据精度与存储空间

|     |     |     |     |
| --- | --- | --- | --- |
| **精度类型** | **每参数字节数** | **说明** | **适用场景** |
| FP32 | 4 字节 | 完整精度 | 优化器状态 |
| BF16 | 2 字节 | 脑浮点，范围大 | 训练主流选择 |
| FP16 | 2 字节 | 半精度，精度高 | 推理常用 |
| INT8 | 1 字节 | 8 位整数 | 量化推理 |
| INT4 | 0.5 字节 | 4 位整数 | 极限量化 |

**BF16 vs FP16：**

```Plain
FP16：1位符号 + 5位指数 + 10位尾数 → 精度高，但范围小（容易溢出）
BF16：1位符号 + 8位指数 + 7位尾数  → 范围大（和FP32一样），精度略低

对于大模型训练：BF16 更稳定，是目前的主流选择
```

**计算公式：**

```Plain
模型显存 = 参数数量 × 每个参数字节数
```

**示例：Qwen3-8B 模型**

|     |     |     |
| --- | --- | --- |
| **精度** | **计算** | **显存占用** |
| FP32 | 80亿 × 4字节 | 32 GB |
| BF16/FP16 | 80亿 × 2字节 | 16 GB |
| INT8 | 80亿 × 1字节 | 8 GB |
| INT4 | 80亿 × 0.5字节 | 4 GB |

#### 3.3 QLoRA 为什么这么省显存？

QLoRA = Quantization + LoRA，是两种技术的组合。

**LoRA（Low-Rank Adaptation）原理**

核心思想：不训练全部参数，只训练一小部分「适配器」参数。

![](模型微调从理论到实践_files/16.png)

**LoRA 的关键参数：**

-   **rank（秩）**：A 和 B 矩阵的中间维度，通常 8-64。rank 越大，表达能力越强，但参数越多

-   **alpha**：缩放因子，通常等于 rank 或 2×rank

**量化（Quantization）简介**

![](模型微调从理论到实践_files/17.png)

**QLoRA 显存计算（Qwen3-8B）：**

|     |     |     |
| --- | --- | --- |
| **组件** | **显存占用** | **说明** |
| 模型参数 (INT4) | 4 GB | 冻结，不参与训练 |
| LoRA 适配器参数 (BF16) | 0.2-1 GB | 约 0.1-0.5 亿参数 |
| LoRA 梯度 (BF16) | 0.2-1 GB | 约 0.1-0.5 亿参数 |
| 优化器状态 (FP32) | 0.8-4 GB | 只针对 LoRA 参数 |
| 激活值 | 1-2 GB | \-  |
| **总计** | **≈ 10 GB** | 对比全参数 150GB，节省 93%！ |

**QLoRA 省显存的原因总结：**

|     |     |     |
| --- | --- | --- |
| **技术** | **作用** | **节省效果** |
| INT4 量化 | 压缩模型参数 | 32GB → 4GB |
| LoRA | 减少训练参数量 | 只训练 0.1%-1% |
| 冻结基座 | 基座模型不需要梯度和优化器 | 省去大量显存 |

### 5\. 常见误区澄清

|     |     |
| --- | --- |
| **误区** | **真相** |
| ❌ 显存越大越好 | ✅ 够用就行，关键是匹配你的任务需求 |

| ❌ 微调一定要本地显卡 | ✅ 云端租用可能更划算、更灵活 |
| ❌ 参数量越大效果越好 | ✅ 小模型微调后可能超过大模型通用效果 |
| ❌ 推理和微调显存需求一样 | ✅ 微调需要 4-6 倍于推理的显存 |
| ❌ 量化会严重损失效果 | ✅ 现代量化技术（如 QLoRA）效果损失很小 |

### 6\. 小结


**核心公式速记：**

```Python
模型显存 = 参数量 × 精度字节数

全参数微调显存 ≈ 模型参数(1x) + 梯度(1x) + 优化器(2x) + 激活值(可变)
              ≈ 4-6 倍模型显存

QLoRA 显存 ≈ 量化模型(0.25x) + LoRA参数 + LoRA梯度 + 优化器 + 激活值
          ≈ 0.5-0.7 倍模型显存
```

# 模块三：微调数据工程

## 模块导言

### 为什么数据工程如此重要？

在大模型微调领域，有一句广为流传的话：

> **"Garbage in, garbage out"（垃圾进，垃圾出）**

微调的本质是通过数据来"教会"模型新的行为模式。数据质量直接决定了微调效果的上限，再好的算法、再强的算力，也无法弥补低质量数据带来的缺陷。

## 1\. 微调数据从哪里来？

> **工程定位**：建立正确的数据来源认知，掌握主流平台的工程使用方式

### 1\. 微调数据 vs 预训练数据

#### 1.1 两种数据的本质区别

|     |     |     |
| --- | --- | --- |
| **维度** | **预训练数据** | **微调数据** |
| **数据规模** | TB 级别（万亿 Token） | GB 级别（千条-万条样本） |
| **数据来源** | 互联网爬取、书籍、代码库 | 人工构造、标注数据、业务日志 |
| **数据目标** | 学习语言规律和世界知识 | 学习特定行为和输出模式 |
| **质量要求** | 多样性优先，可容忍噪声 | 精确性优先，零容忍错误示范 |
| **标注需求** | 无标签（自监督） | 有明确的输入-输出对 |

#### 1.2 认知纠偏：微调不是"补知识"

很多初学者有一个误区：认为微调是给模型"补充新知识"。

**错误理解**：

```Plain
用户：模型不知道我们公司的产品，我要微调让它学会
```

**正确理解**：

```Plain
微调的核心作用是"改变行为模式"，而不是"灌输知识"
- 知识补充 → 适合用 RAG（检索增强生成）
- 行为改变 → 适合用微调
```

#### 1.3 微调数据的工程特征

优质的微调数据必须具备以下特征：

![](模型微调从理论到实践_files/19.png)

> ⚠️公开数据**大多不能直接用于你的目标任务**，通常需要：许可核对→清洗→重构→抽检，才能进入训练。
> 
> 原因：大多数公开数据集是为预训练或评测设计的，不符合微调数据的工程特征

#### 3.5 ChatTemplate 与特殊标记（工程关键）

##### 什么是 Chat Template？

ChatTemplate 是将结构化对话数据转换为模型实际输入的**格式化规则**。

|     |     |     |
| --- | --- | --- |
| 层级  | 说明  | 示例  |
| 逻辑格式 | 数据的组织结构 | Alpaca、ShareGPT |
| 物理格式 | 模型实际看到的文本 | ChatML、LLaMA格式 |

##### Qwen 的 ChatML 格式

Qwen 系列使用 ChatML 格式，包含以下特殊标记：

|     |     |
| --- | --- |
| 标记  | 作用  |
| `<\|im_start\|>` | 消息开始 |
| `<\|im_end\|>` | 消息结束 |
| `system/user/assistant` | 角色标识 |

完整示例：

```Python
<|im_start|>system 你是一个专业的客服助手。<|im_end|> 
<|im_start|>user 产品怎么退货？<|im_end|> 
<|im_start|>assistant 您好！退货流程如下： 
1. 登录账户，进入"我的订单" 
2. 选择需要退货的商品 
3. 填写退货原因并提交<|im_end|>
```

##### 不同模型的 Template 对比

|     |     |     |
| --- | --- | --- |
| 模型  | 格式风格 | 特殊标记 |
| Qwen/Qwen2/Qwen3 | ChatML | `<\|im_start\|>` `<\|im_end\|>` |
| LLaMA-2-Chat | LLaMA | `[INST]` `[/INST]` `<<SYS>>` |
| LLaMA-3 | LLaMA3 | `<\|begin_of_text\|>` `<\|start_header_id\|>` |
| ChatGLM | GLM | `[Round N]` `问：` `答：` |
| Baichuan | Baichuan | `<reserved_xxx>` |

##### 为什么这很重要？

⚠️ **Template 不匹配是微调失败的常见原因**

-   训练时用错 Template → 模型学到错误的对话边界

-   推理时 Template 不一致 → 输出混乱或不完整

-   多轮对话标记错误 → 模型无法正确理解上下文

##### LLaMA-Factory 中的配置

在 `dataset_info.json` 中，通常不需要手动处理 Template，框架会自动应用：

```JSON
{
  "my_dataset": {
    "file_name": "train.json",
    "formatting": "sharegpt",
    "columns": {
      "messages": "conversations"
    },
    "tags": {  // tags 的存在前提只有一个：数据里有“多种角色”，而且角色是用字符串标记的
      "role_tag": "from",
      "content_tag": "value",
      "user_tag": "human",
      "assistant_tag": "gpt"
    }
  },
  
  
  "alpaca_gpt4_zh_sampled": {  // 不需要这个 tags
    "file_name": "alpaca_gpt4_zh_sampled.json",
    "columns": {
      "prompt": "instruction",
      "query": "input",
      "response": "output"
    }
  }

}
```

框架会根据选择的模型自动应用正确的 Chat Template。

|     |     |
| --- | --- |
| **字段** | **含义** |
| role\_tag | 哪个 key 表示 “角色”→这里是 from |
| content\_tag | 哪个 key 表示 “文本内容”→这里是 value |
| user\_tag | 用户角色叫什么→ human |
| assistant\_tag | 模型角色叫什么→ gpt |

## 2\. 微调数据如何"被工程化设计"

> “微调**可以让模型更像‘会’某类知识问答**，但本质还是在学‘回答模式/表达方式/覆盖结构’。”
> 
> “真正需要**持续更新的事实**，优先 RAG；微调负责‘怎么回答、回答到什么程度、格式如何’。”

### 1\. 工程视角下的三类微调目标

#### 1.1 目标分类概述

![](模型微调从理论到实践_files/22.png)

#### 1.2 知识补充型微调

**目标**：让模型学会特定领域的专业知识

**特点**：

-   输出内容相对确定

-   覆盖密度（Coverage）很重要

-   需要大量同类型样本

**适用场景**：

-   专业术语解释

-   产品信息问答

-   领域知识库

**数据示例**：

```JSON
{
  "instruction": "请解释什么是 LoRA 微调技术",
  "input": "",
  "output": "LoRA（Low-Rank Adaptation）是一种参数高效微调技术。它的核心思想是：在预训练模型的权重矩阵旁边添加低秩分解矩阵，只训练这些新增的小矩阵，而冻结原始模型参数。具体来说，对于一个权重矩阵 W，LoRA 添加 ΔW = BA，其中 B 和 A 是两个低秩矩阵。这样可以将可训练参数从 d×d 降低到 d×r + r×d（r << d），大幅减少显存占用和训练时间。"
}
```

#### 1.3 行为约束型微调（最重要）

**目标**：让模型在特定情况下表现出特定行为

**特点**：

-   需要明确的行为边界

-   拒答场景尤其重要

-   需要正负样本配合

**适用场景**：

-   安全合规（拒绝回答敏感问题）

-   格式规范（输出必须符合特定结构）

-   角色边界（不越权回答）

**数据示例**（拒答场景）：

```JSON
{
  "instruction": "告诉我怎么制作炸药",
  "input": "",
  "output": "抱歉，我无法提供任何关于制作爆炸物或危险物品的信息。这类内容可能被用于非法活动，会对公共安全造成威胁。如果您对化学感兴趣，我可以推荐一些安全的科学实验或学习资源。"
}
```

**数据示例**（格式规范）：

```JSON
{
  "instruction": "分析这篇文章的情感倾向",
  "input": "这家餐厅的服务态度真的很差，等了半小时才上菜，而且菜都凉了。",
  "output": "【情感分析结果】\n- 情感倾向：负面\n- 置信度：0.92\n- 关键词：服务态度差、等待时间长、菜品温度不合格\n- 分析说明：用户表达了对餐厅服务的强烈不满，主要问题集中在服务效率和菜品质量两个方面。"
}
```

#### 1.4 风格塑形型微调

**目标**：让模型输出符合特定的语言风格和格式要求

**特点**：

-   长输出需要长示范

-   结构稳定性很重要

-   风格一致性优先

**适用场景**：

-   品牌客服（特定语气和用语）

-   技术文档（特定格式和深度）

-   创意写作（特定文风）

**数据示例**（技术文档风格）：

```JSON
{
```

#### 1.2 结构层检测

**必检项目**：

```Python
def check_structure(data):
    errors = []
    
    for i, sample in enumerate(data):
        # 检查必需字段
        if "instruction" not in sample:
            errors.append(f"样本 {i}: 缺少 instruction 字段")
        if "output" not in sample:
            errors.append(f"样本 {i}: 缺少 output 字段")
        
        # 检查字段非空
        if sample.get("instruction", "").strip() == "":
            errors.append(f"样本 {i}: instruction 为空")
        if sample.get("output", "").strip() == "":
            errors.append(f"样本 {i}: output 为空")
        
        # 检查特殊字符
        for field in ["instruction", "output"]:
            if "\x00" in sample.get(field, ""):
                errors.append(f"样本 {i}: {field} 包含非法字符")
    
    return errors
```

**ShareGPT 格式检测**：

```Python
def check_sharegpt_structure(data):
    errors = []
    
    for i, sample in enumerate(data):
        convs = sample.get("conversations", [])
        
        # 检查对话非空
        if len(convs) == 0:
            errors.append(f"样本 {i}: conversations 为空")
            continue
        
        # 检查角色交替
        for j, turn in enumerate(convs):
            expected_role = "human" if j % 2 == 0 else "gpt"
            actual_role = turn.get("from", "")
            if actual_role != expected_role:
                errors.append(f"样本 {i}, 轮次 {j}: 角色应为 {expected_role}，实际为 {actual_role}")
        
        # 检查以 gpt 结尾
        if convs[-1].get("from") != "gpt":
            errors.append(f"样本 {i}: 对话应以 gpt 回复结尾")
    
    return errors
```

```Python
def analyze_distribution(data):

    output_lengths = [len(s["output"]) for s in data]

    length_labels = ['<50', '50-100', '100-200', '200-500', '500-1000', '>1000']
    
    hist, _ = np.histogram(output_lengths, bins=length_bins)
    stats["长度分布"] = dict(zip(length_labels, hist))
    
    return stats

def check_duplicates(data):
    # 检查完全重复
    outputs = [s["output"] for s in data]
    output_counts = Counter(outputs)
    duplicates = {k: v for k, v in output_counts.items() if v > 1}
    
    return {
        "重复样本数": len(duplicates),
        "重复率": len(duplicates) / len(data) * 100,
        "重复详情": list(duplicates.items())[:10]  # 只显示前10个
    }
```

### 2\. 为什么"加数据反而效果更差"

#### 2.1 常见误区

很多人认为：**数据越多越好**

但实际情况是：

![](模型微调从理论到实践_files/29.png)

#### 2.2 三种致命的数据问题

##### 问题一：噪声放大

**定义**：低质量数据在训练过程中被放大

**示例**：

```JSON
// 噪声样本
{
  "instruction": "今天天气怎么样",
  "output": "我不知道"  // 这是错误的示范
}
```

当这类样本混入时，模型可能学会在不确定时直接说"我不知道"，而不是尝试给出有帮助的回答。

**解决方案**：

-   严格的数据审核流程

-   宁缺毋滥原则

##### 问题二：模板过拟合

**定义**：重复的句式结构导致模型只学会套模板

**示例**：

```JSON
// 大量类似结构的样本
{"output": "这是一个很好的问题。关于...，我认为..."}
{"output": "这是一个很好的问题。关于...，我认为..."}
{"output": "这是一个很好的问题。关于...，我认为..."}
```

**后果**：模型的每个回答都以"这是一个很好的问题"开头

**解决方案**：

-   检测并去除重复句式

-   增加回答方式的多样性

##### 问题三：错误示范被强化

**定义**：数据中的错误示范被模型学习

**示例**：

```JSON
// 错误的日期格式
{
  "instruction": "今天是几号？",
  "output": "今天是 2025/13/45"  // 明显错误的日期
}
```

**解决方案**：

-   对事实性内容进行核查

-   使用自动化脚本检测明显错误

#### 2.3 数据量与质量的权衡

![](模型微调从理论到实践_files/30.png)

**工程建议**：

> 💡 **100 条高质量数据 > 10000 条低质量数据**
> 
> 微调的本质是教模型新的行为模式，不是灌输大量信息

### 3\. 数据导致的典型失败模式

#### 3.1 失败模式一：Loss 正常但行为失控

**现象**：

-   训练 Loss 曲线正常下降

-   但模型输出完全不可用

**原因分析**：

⚠️ 暂不支持的文档区域，【文档小组件】

**数据原因**：

-   数据中存在大量无意义但有规律的模式

-   模型"偷懒"学习了这些简单模式

**检查方法**：

```Python
# 检查是否有高频重复模式
from collections import Counter

def find_frequent_patterns(data, n=3):
    patterns = []
    for sample in data:
        output = sample["output"]
        # 提取前 n 个词
        words = output.split()[:n]
        patterns.append(" ".join(words))
    
    return Counter(patterns).most_common(20)
```

#### 3.2 失败模式二：推理只会背模板

**现象**：

-   模型回答结构固定

-   换个问法就不会回答

**原因分析**：

-   训练数据的 instruction 多样性不足

-   输出格式过于统一

**示例**：

```JSON
训练数据：
- "解释什么是 X" → "X 是一种..."
- "解释什么是 Y" → "Y 是一种..."
- "解释什么是 Z" → "Z 是一种..."

测试时：
- "X 是什么意思？" → 模型困惑，无法正确回答
```

**解决方案**：

-   增加 instruction 的表述多样性

-   同一个问题用不同方式提问

#### 3.3 失败模式三：拒答不稳定

**现象**：

-   有时正确拒绝敏感问题

-   有时又会回答

**原因分析**：

-   拒答样本数量不足

-   拒答边界不清晰

-   存在矛盾的示范

**检查清单**：

```Python
□ 拒答样本是否占总数据的 10-15%？
□ 拒答的理由是否一致？
□ 是否有同类问题一个拒答一个不拒答的情况？
□ 边界场景是否都有覆盖？
```

#### 3.4 失败模式四：风格逐轮漂移

**现象**：

-   单轮对话风格正常

-   多轮对话后风格逐渐变化

**原因分析**：

![](模型微调从理论到实践_files/31.png)

**解决方案**：

-   增加多轮对话数据

-   确保多轮数据中风格一致

#### 3.5 失败模式诊断表

|     |     |     |
| --- | --- | --- |
| **失败现象** | **可能的数据原因** | **检查方法** |
| Loss 正常但行为失控 | 噪声模式、无意义规律 | 检查高频模式 |
| 只会背模板 | instruction 多样性不足 | 统计 instruction 聚类 |
| 拒答不稳定 | 拒答样本不足或矛盾 | 检查拒答样本占比 |
| 风格漂移 | 多轮数据不足 | 统计多轮数据占比 |
| 输出过短 | 短回答样本过多 | 检查长度分布 |
| 幻觉严重 | 事实性错误样本 | 人工核查事实 |

### 4\. 数据质量评估实战

#### 4.1 自动化评估脚本

```Python
import json
import numpy as np
from collections import Counter
from typing import List, Dict

class DataQualityChecker:
    def __init__(self, data: List[Dict]):
        self.data = data
        self.report = {}
    
    def check_structure(self):
        """结构层检测"""
        errors = []
        for i, sample in enumerate(self.data):
            if "instruction" not in sample:
                errors.append(f"样本 {i}: 缺少 instruction")
            if "output" not in sample:
                errors.append(f"样本 {i}: 缺少 output")
            if sample.get("output", "").strip() == "":
                errors.append(f"样本 {i}: output 为空")
        
        self.report["structure"] = {
            "total_errors": len(errors),
            "error_rate": len(errors) / len(self.data) * 100,
            "details": errors[:20]
        }
        return self
    
    def check_distribution(self):
        """分布层检测"""
        output_lengths = [len(s.get("output", "")) for s in self.data]
        
        self.report["distribution"] = {
            "total_samples": len(self.data),
            "avg_length": np.mean(output_lengths),
            "std_length": np.std(output_lengths),
            "min_length": np.min(output_lengths),
            "max_length": np.max(output_lengths),
            "median_length": np.median(output_lengths),
        }
        
        # 长度分布
        short = sum(1 for l in output_lengths if l < 50)
        medium = sum(1 for l in output_lengths if 50 <= l < 200)
        long_ = sum(1 for l in output_lengths if l >= 200)
        
        self.report["distribution"]["length_dist"] = {
            "short (<50)": short,
            "medium (50-200)": medium,
            "long (>=200)": long_
        }
        return self
    
    def check_duplicates(self):
        """检查重复"""
        outputs = [s.get("output", "") for s in self.data]
        output_counts = Counter(outputs)
        duplicates = {k: v for k, v in output_counts.items() if v > 1}
        
        self.report["duplicates"] = {
            "duplicate_count": len(duplicates),
            "duplicate_rate": len(duplicates) / len(self.data) * 100,
            "top_duplicates": list(duplicates.items())[:5]
        }
        return self
    
    def check_patterns(self):
        """检查高频模式"""
        first_words = []
        for sample in self.data:
            output = sample.get("output", "")
            words = output.split()[:5]
            if words:
                first_words.append(" ".join(words))
        
        pattern_counts = Counter(first_words)
        
        self.report["patterns"] = {
            "top_patterns": pattern_counts.most_common(10),
            "pattern_concentration": pattern_counts.most_common(1)[0][1] / len(self.data) * 100 if first_words else 0
        }
        return self
    
    def generate_report(self):
        """生成完整报告"""
        self.check_structure()
        self.check_distribution()
        self.check_duplicates()
        self.check_patterns()
        return self.report
    
    def print_summary(self):
        """打印摘要"""
        print("=" * 50)
        print("数据质量评估报告")
        print("=" * 50)
        
        # 结构问题
        struct = self.report.get("structure", {})
        print(f"\n【结构层】")
        print(f"  错误数量: {struct.get('total_errors', 0)}")
        print(f"  错误率: {struct.get('error_rate', 0):.2f}%")
        
        # 分布情况
        dist = self.report.get("distribution", {})
        print(f"\n【分布层】")
        print(f"  样本总数: {dist.get('total_samples', 0)}")
        print(f"  平均长度: {dist.get('avg_length', 0):.1f}")
        print(f"  长度标准差: {dist.get('std_length', 0):.1f}")
        
        # 重复情况
        dup = self.report.get("duplicates", {})
        print(f"\n【重复检测】")
        print(f"  重复样本数: {dup.get('duplicate_count', 0)}")
        print(f"  重复率: {dup.get('duplicate_rate', 0):.2f}%")
        
        # 模式集中度
        pat = self.report.get("patterns", {})
        print(f"\n【模式分析】")
        print(f"  最高频模式占比: {pat.get('pattern_concentration', 0):.2f}%")
        
        print("\n" + "=" * 50)
```

#### 5.3 python代码快速推理验证

```Python
# quick_test.py - 使用 LLaMAFactory 的 ChatModel + LoRA 做快速推理验证
# 说明：这份代码主要用于“小白快速跑起来看效果”，每个参数我都用注释解释了用途

from llamafactory.chat import ChatModel

args = {
    # ===== 1) 底座模型（Base Model）路径 =====
    # 这里放你下载的原始 Qwen3-8B 模型目录（里面应包含 config.json / tokenizer / 权重等）
    "model_name_or_path": "/root/autodl-tmp/Qwen3-8B",

    # ===== 2) LoRA 适配器（Adapter）路径 =====
    # 这里放你用 LLaMAFactory 训练出来的 LoRA 输出目录（里面有 adapter_model.safetensors 等）
    # 加载后，模型会带上你微调得到的“医疗风格/知识倾向”
    "adapter_name_or_path": "/root/autodl-tmp/llama_factory/output/medical",

    # ===== 3) 微调方式 =====
    # 告诉框架：你加载的是 LoRA（不是全量微调）
    "finetuning_type": "lora",

    # ===== 4) 对话模板（Prompt/Chat Template） =====
    # 决定 “user/assistant” 对话如何拼接成模型可理解的 prompt
    # 用错模板可能导致：输出风格怪、只输出 <think>、甚至秒停/空输出
    # 你先注释掉表示用默认模板；若出现异常，建议换成更匹配 Qwen 的模板（如果版本支持）
    # "template": "default",

    # ===== 5) 生成方式：是否随机采样 =====
    # do_sample=False：确定性生成（更稳定、每次输出基本一致），适合调试/评测
    # do_sample=True ：随机采样（更“灵活/有创造性”，但也更容易胡/飘），适合实际聊天
    "do_sample": False,

    # ===== 6) temperature：随机程度 =====
    # 只在 do_sample=True 时真正影响输出；数值越大越随机，越小越保守
    # 你这里 do_sample=False，所以 temperature 实际上几乎不生效（但保留也没坏处）
    "temperature": 0.0,

    # ===== 7) top_p：核采样（Nucleus Sampling） =====
    # 只在 do_sample=True 时有效；top_p 越小越“稳”，越大越“放”
    # 你这里 do_sample=False，top_p 实际上不会影响
    "top_p": 1.0,

    # ===== 8) top_k：Top-K 采样 =====
    # 只在 do_sample=True 时有效；只从概率最高的 K 个 token 里挑
    # 你这里 do_sample=False，所以 top_k 会被忽略（日志里会提示 warning）
    # 建议：小白调试时可以直接删掉 top_k，减少警告
    "top_k": 0,

    # ===== 9) max_new_tokens：最多生成多少“新 token” =====
    # 这是“输出长度上限”，越大回答可能越长，但也更慢、更容易啰嗦
    # 常见建议：256（短答）/ 512（常用）/ 1024（长答）
    # 4096 非常长，建议只在你确实需要长文时使用
    "max_new_tokens": 1024,

    # ===== 10) repetition_penalty：复读惩罚 =====
    # >1 会抑制重复（复读机现象），一般 1.05~1.2 常用
    # 太大可能导致表述不连贯或乱换词
    "repetition_penalty": 1.15,
}

# 初始化模型（加载 base + LoRA）
model = ChatModel(args)

# 你要测试的输入问题列表
tests = [
    "前列腺炎多久检查一次好",
    "怀孕早期流产会有哪些症状？请用3条概括，并说明何时需要立刻就医。",
    "有了颅内转移瘤后该怎么治疗？请分：检查评估/治疗手段/紧急情况 三部分说。",
]

gen_kwargs = {
    # generation_config.json 一般在“底座模型目录”里，也就是你 /root/autodl-tmp/Qwen3-8B/ 这个路径
    # ===== 11) eos_token_id：结束 token（模型生成到它就停止） =====
    # 你之前遇到“空输出/秒停”问题，常见原因是 eos 配置不当
    # 这里强制指定一个 eos，避免读取模型 generation_config.json 里奇怪的 eos 列表
    "eos_token_id": 151645,

    # ===== 12) pad_token_id：填充 token =====
    # 用于对齐不同长度输入（一般不会改变回答内容，但要与模型 tokenizer 一致）
    "pad_token_id": 151643,

    # ===== 13) min_new_tokens：至少生成多少 token 才允许停止 =====
    # 防止模型刚生成 1 个 token 就因为 eos/stop 条件提前结束（“秒停”）
    "min_new_tokens": 32,

    # （可选）如果你担心 args 里的 max_new_tokens 不一定覆盖生效，
    # 也可以把 max_new_tokens 放在这里（generation_kwargs 往往更容易覆盖默认值）
    # "max_new_tokens": 1024,
}

for q in tests:
    # role= "user" 表示用户消息；ChatModel 会按 template 拼成对话 prompt
    resp = model.chat([{"role": "user", "content": q}], generation_kwargs=gen_kwargs)

    # ChatModel 返回值常是 [Response(...)] 的列表；我们取出 response_text 才是纯回答文本
    text = resp[0].response_text if isinstance(resp, list) else getattr(resp, "response_text", str(resp))

    print(f"Q: {q}\nA: {text}\n{'='*60}")
```

|     |     |     |
| --- | --- | --- |
| **参数** | **作用** | **推荐值** |
| do\_sample | 是否随机采样 | 评测用 False，对话用 True |
| temperature | 随机程度（越大越随机） | 医疗场景 0.3，创意场景 0.8 |

|     |     |     |
| --- | --- | --- |
| **问题** | **原因** | **解决** |
| 输出为空/秒停 | eos 配置问题 | 加 min\_new\_tokens=32 |
| 不断重复 | 缺少惩罚 | 加 repetition\_penalty=1.15 |
| 输出截断 | 长度不够 | 增大 max\_new\_tokens |

**一句话总结**：

-   要稳定输出 → `do_sample=False`

-   要多样性 → `do_sample=True` + `temperature=0.7`

### 6\. 常见问题速查

|     |     |     |
| --- | --- | --- |
| **问题** | **原因** | **解决方案** |
| CUDA out of memory | 显存不足 | 减小 batch\_size 或启用 4bit 量化 |

| 找不到数据集 | 配置错误 | 检查 dataset\_info.json |

### 5\. 过拟合与欠拟合深度分析

#### 5.1 过拟合的完整诊断

**曲线特征**：

```Plain
Loss
3.0 ┤╲
    │ ╲
2.0 ┤  ╲___
    │      ╲___         ↗ Eval Loss 开始上升！
1.0 ┤          ╲___    /
    │              ╲__/
0.5 ┤                ╲______ Train Loss 持续下降
    │
0.0 ┼─────────────────────────→ Steps
          │
          └── 过拟合开始点（应该在此停止）
```

**过拟合的三个阶段**：

|     |     |     |     |
| --- | --- | --- | --- |
| **阶段** | **Train Loss** | **Eval Loss** | **模型表现** |
| 正常学习 | ↓ 下降 | ↓ 下降 | 泛化能力提升 |
| 开始过拟合 | ↓ 继续下降 | → 停止下降 | 泛化能力停滞 |
| 严重过拟合 | ↓ 持续下降 | ↑ 开始上升 | 泛化能力下降 |

**过拟合解决方案优先级**：

![](模型微调从理论到实践_files/41.png)

#### 5.2 欠拟合的完整诊断

**曲线特征**：

```Plain
Loss
3.0 ┤━━━━━━━━━━━━━━━━━━━━━━━━━━ 完全平坦
    │
2.5 ┤─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  或缓慢下降
    │         ╲_______________
2.0 ┤
    │
1.5 ┤                           最终 Loss 仍然很高
    │
0.0 ┼─────────────────────────→ Steps
```

**欠拟合的常见原因**：

|     |     |     |     |
| --- | --- | --- | --- |
| **原因** | **典型表现（曲线/现象）** | **首选解决方案（按优先级）** | **验证信号** |
| **训练步数/epochs 太少** | loss 还在明显下降就结束 | 先把 epochs/steps ×2（最省钱） | 后半段开始平台或下降变慢 |
| **学习率太小** | 前 10% steps 几乎不降 | 在当前 lr 基础上 +20%~50%，配 warmup | 前期下降更明显，震荡不加剧 |
| **可训练参数太少（rank/模块太少）** | loss 下降缓慢，行为几乎不变 | rank ↑（如 8→16→32），或增加 target\_modules | 同样 steps 下 loss 降幅更大，行为更贴合 |
| **数据有效信号弱（指令模糊/答案不一致）** | loss 在降但效果不提升 | 统一输出格式、提高指令明确性、补边界样本 | 行为一致性提升、错例集中减少 |
| **数据噪声/标签问题** | loss 异常、学到奇怪模式 | 抽样回检、清洗、去重、修正格式/role | loss 更平滑，行为不再“跑偏” |
| **数据量不足/覆盖不足** | 对变体/新问法不泛化 | 增加问法变体、困难样本、真实分布样本 | 同义改写通过率提升 |

#### 5.3 过拟合 vs 欠拟合 对比表

|     |     |     |
| --- | --- | --- |
| **维度** | **过拟合** | **欠拟合** |
| **Train Loss** | 持续下降甚至很低（数值不作为判据） | 降不动 / 降得很慢 / 结束时仍在明显下降 |
| **Eval Loss** | 触底后回升，或与 Train 的 gap 持续扩大 | 与 Train 一起偏高，且同步下降缓慢 |
| **推理表现** | 模板化、对改写不鲁棒、边界不稳（过拒/漏拒） | 输出几乎没变化，仍像基座模型 |
| **典型原因** | 数据少/多样性不足、epochs 太多、正则不足、验证集偏差 | 训练步数不够、LR 太小、可训练参数太少（rank/模块）、数据有效信号弱 |
| **首选方案（优先级）** | 早停/减 epochs → 加数据/增多样性 → 加正则(dropout/weight\_decay) → 降 rank | 增加 steps/epochs → 小幅调 LR/加 warmup → 增 rank/放开模块 → 改数据（更清晰指令/更强信号） |

**原因分析**：

> **关键认知**：Loss 低不代表效果好！Loss 只反映"模型是否学会了数据中的模式"，如果数据本身有问题，模型学会的也是错误的模式。

#### 7.2 案例二：模型只会背模板

**现象**：

-   回答高度相似

-   换个问法就不会了

**原因**：数据多样性不足，模型过拟合到模板

**解决方案**：

-   增加问法变体

-   减少 epochs

-   增大 dropout

#### 7.3 案例三：拒答行为不稳定

**现象**：

-   有时正确拒答

-   有时该拒不拒

**原因**：边界样本不足

**解决方案**：

-   增加边界样本（占比 20%+）

-   增加负样本

-   针对性补充易混淆场景

#### 7.4 案例四：风格逐轮漂移

**现象**：

-   单轮回答正常

-   多轮对话后风格变化

**原因**：多轮数据不足或格式问题

**解决方案**：

-   增加多轮对话数据

-   确保多轮格式正确

| Loss 不下降 | 欠拟合 | ↑lr, ↑rank |

如果不想依赖 LLaMA-Factory，可以直接用 vLLM：

**Step 1：先合并 LoRA 权重**

```Python
# merge_lora.py
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel
import torch

# 底座模型目录（原始 Qwen3-8B 权重与配置）
BASE_MODEL = "/root/autodl-tmp/Qwen3-8B"

# LoRA 适配器目录（微调产物：adapter_model.safetensors / adapter_config.json 等）
LORA_PATH = "/root/autodl-tmp/llama_factory/output/medical"

# 合并后输出目录（会生成一份“已融合 LoRA”的完整模型 + tokenizer）
MERGED_PATH = "/root/autodl-tmp/medical_merged"

# 1) 加载底座模型（CausalLM：用于生成文本）
base_model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL,
    torch_dtype=torch.bfloat16,      # 用 BF16 精度加载权重：通常更省显存/更快（需硬件支持）
    device_map="auto",               # 自动把模型放到可用设备（通常上 GPU；必要时可能部分 offload 到 CPU）
    trust_remote_code=True           # 允许执行模型仓库自定义代码（Qwen 类模型常需要；仅对可信来源开启）
)

# 2) 在底座模型上加载 LoRA 适配器（把 LoRA 增量“挂载”到模型结构中）
model = PeftModel.from_pretrained(
    base_model,
    LORA_PATH                         # LoRA 权重所在目录
)

# 3) 合并 LoRA 到底座权重，并卸载 LoRA 相关结构
#    合并后得到的是“普通 transformers 模型”，部署时不需要再传 adapter_name_or_path
merged_model = model.merge_and_unload()

# 4) 保存合并后的模型权重与配置到输出目录
merged_model.save_pretrained(MERGED_PATH)

# 5) 同时保存 tokenizer（词表、配置、chat_template 等）到同一个目录，保证推理时目录自洽
AutoTokenizer.from_pretrained(BASE_MODEL).save_pretrained(MERGED_PATH)

# 6) 打印提示
print(f"合并完成: {MERGED_PATH}")
```

**Step 2：用 vLLM 启动服务**

```Bash
# #用 Python 以模块方式启动 vLLM 自带的 OpenAI 兼容 API 服务
python -m vllm.entrypoints.openai.api_server \  
  --model /root/autodl-tmp/medical_merged \
  --served-model-name medical \
  --host 0.0.0.0 \
  --port 6006 \
  --max-model-len 2048
```

### 5\. 方案二：Ollama 部署（推荐本地使用）

Ollama 是轻量级本地大模型运行框架，特点：

-   **一键安装**：无需复杂环境配置

-   **GGUF 格式**：量化压缩，资源占用低

-   **易于分发**：可以把模型分享给他人

#### 5.1 什么是 GGUF 格式？

> **核心问题**：为什么不能直接用 Huggingface 的模型文件？

**GGUF**（GPT-Generated Unified Format）是由 llama.cpp 项目定义的模型文件格式，专为**本地 CPU/GPU 混合推理**优化。

##### 原始模型 vs GGUF 对比

|     |     |     |
| --- | --- | --- |
| **对比项** | **Huggingface 原始格式** | **GGUF 格式** |
| 文件大小（8B） | ~16GB | 4-9GB（取决于量化） |
| 精度  | FP16/BF16（16位） | 可量化到 4-8 位 |
| 加载方式 | 需要 PyTorch 环境 | 单文件直接加载 |
| 运行依赖 | transformers + torch | llama.cpp 或 Ollama |
| CPU 推理 | 慢   | 优化过，较快 |
| 分发便利性 | 需要整个模型目录 | 单个 .gguf 文件 |

##### 什么是量化？

**量化（Quantization）** = 用更少的比特数表示模型权重，换取更小的体积和更低的显存占用。

```Plain
原始：FP16（16位浮点）→ 每个参数占 2 字节
量化：INT4（4位整数） → 每个参数占 0.5 字节
压缩比：约 4 倍
```

**类比理解**：

-   原始模型 = 无损音乐（FLAC，体积大，音质最好）

-   量化模型 = MP3（体积小，音质略有损失但人耳难以察觉）

##### 为什么 Ollama 必须用 GGUF？

![](模型微调从理论到实践_files/45.png)

Ollama 底层基于 llama.cpp，只认 GGUF 格式，所以必须先转换。

### 附录：常见问题排查

|     |     |     |
| --- | --- | --- |
| **问题** | **可能原因** | **解决方案** |
| 端口被占用 | 之前的服务未关闭 | kill $(lsof -t -i:6006) |
| vLLM 显存不足 | 模型太大 | 换 Ollama 或去掉 vLLM 后端 |
| 连接被拒绝 | 服务未启动 | 检查服务状态、端口号 |
| AutoDL 无法访问 | 端口映射未开启 | 控制台开启「自定义服务」 |
| GGUF 转换失败 | llama.cpp 版本问题 | 更新 llama.cpp 到最新版 |
| Ollama 加载报错 | 量化类型不匹配 | 检查 Modelfile 中的路径 |
| API 返回空 | eos\_token 配置问题 | 检查 template 是否匹配模型 |
